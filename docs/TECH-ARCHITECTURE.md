# DeuceX: technical architecture and build plan

Version 0.4, 14 September 2026. Owner: Manu Dubey. Companion to PRD-00 through PRD-13 and the review register. Change from 0.1: reflects the twenty decisions settled on 13 September (worksheet 1 to 17 and A18 to A20) and the admin console (PRD-13): schema additions for payouts, deletion cooling-off, reviewed fan answers, share-link renewal and the staff side; a new epic E18; the build plan and risk list updated. This document answers how DeuceX gets built. The thirteen requirements documents say what it does; this one says what stack, what schema, what orchestration, what it costs to run, and in what order a team of three to five engineers should build it. Where a number cannot be verified against a live vendor quote, it is marked as an estimate and shown with its working, not asserted as fact.

## 1. Stack recommendation

### Web and mobile: one codebase, mobile-first, and whether a PWA is enough

The prototype already answers half the frontend question. `deucex-dashboard.html` is a single-file shadcn/ui Vega preset build (Neutral base, Lime chart palette, Geist and Geist Mono, Base UI primitives, 0.625rem radius) with hash routing, a working offline queue pattern, translucent chrome, and a full dark and light token set. None of that design work needs redoing. The recommendation is to port the design tokens and component recipes into a proper component library (Tailwind config plus a small set of Base UI or Radix primitives styled to match) inside a Next.js app, rather than reinvent the visual system. The porting effort is real but bounded: it is CSS variables, a handful of component recipes (card, button, badge, tabs, toggle group, table) and the SVG chart helpers, not new design.

The harder question is whether a progressive web app is enough for the actual job: voice capture up to 60 seconds, camera capture for menus and receipts, and an offline queue that survives a hotel corridor with no signal. On Android, a PWA is genuinely enough. `getUserMedia` and `MediaRecorder` give reliable microphone capture, the camera input with `capture` attribute or `getUserMedia` gives photo capture, a service worker plus IndexedDB gives a durable offline queue, and the Background Sync API lets a queued upload retry itself even if the tab is closed. Push notifications work through the Web Push API once the PWA is installed.

On iOS, the honest answer is that a PWA is not fully enough. Safari supports `MediaRecorder` and camera capture reasonably well as of recent iOS versions, but it has no Background Sync API, so a queued voice note or receipt photo only uploads reliably while the app is foregrounded, not overnight from a phone in a bag. Web Push on iOS only works from an installed home-screen PWA, only from iOS 16.4 onward, and install friction (the player has to know to use the share sheet) measurably reduces how many players ever get push notifications at all. Given that morning notifications and deadline alerts are core to the "three answers in ten seconds" promise, this is a real gap, not a nice-to-have.

The recommendation is therefore: build one PWA (Next.js, installable, offline-capable) as the only web surface for Release 1, and wrap it in a thin native shell using Capacitor for iOS and Android app store distribution. Capacitor keeps the entire UI and business logic in the web codebase, no second implementation for a three to five person team to maintain, while giving native APIs for reliable background upload retry, native push, and an App Store presence that a paid subscription product needs. Full native (Swift or Kotlin, or React Native and Expo) is not recommended for Release 1: it roughly doubles ongoing engineering surface, and nothing in the PRDs needs a capability Capacitor cannot expose. Revisit native only if App Store review friction on Capacitor wrappers becomes a real blocker, a Release 2 or 3 decision, not a Release 1 one.

### API, database, background jobs, storage, hosting

API: a TypeScript Node service (Fastify, chosen over NestJS for less ceremony at this team size) sitting behind the Next.js app, handling agent orchestration, webhooks (Stripe, Resend) and the structured-output calls. Next.js server actions handle simple CRUD directly against the database; the Fastify service owns anything with an external side effect or a scheduled job, which keeps the approval-gate boundary (section 3) architecturally clean rather than scattered across API routes.

Database: PostgreSQL. The money model (section 5.3 of PRD-00, M-DATA-1, M-DATA-2) needs real transactional integrity, foreign keys and check constraints; a document database would make "never overwrite a locked rate" and "a receivable stays out of reserves until received" harder to enforce, not easier. Managed Postgres via Supabase is the recommended starting point: it bundles row-level security (useful for per-player isolation, section 6), auth, and realtime subscriptions for a small team, at the cost of some vendor lock-in. Neon or plain RDS Postgres plus a separate auth provider is the honest alternative if the owner wants to avoid that lock-in; it costs a few extra weeks of plumbing for auth and RLS-equivalent policies at the application layer.

Background jobs and scheduling: given the number of crons in this product (Sunday 20:00 UTC Tournament Agent, daily 07:00 UTC Financial Agent, daily local-time Mindset Coach, daily 06:00 Fans attention pass, weekly Monday Sponsor Agent review, nightly 02:00 UTC overnight analysis), a job queue is not optional. Because the team is already committed to Postgres, the recommendation is a Postgres-backed queue (graphile-worker or pg-boss) rather than standing up Redis purely for BullMQ, which keeps operational surface area small. If job volume grows enough that Postgres-as-queue becomes a bottleneck, Redis and BullMQ is the natural next step, a scaling problem worth having later, not a Release 1 concern.

Object storage: Cloudflare R2 for audio and photos, matching the retention pattern the prototype already assumes (player-scoped keys, no egress fees, S3-compatible API so any client library works unchanged).

Hosting: Vercel for the Next.js frontend, Fly.io or Render for the Fastify API and worker processes (both need long-running processes for cron and queue workers, which Vercel's serverless model does not suit well), Supabase or Neon for Postgres, Cloudflare R2 for storage. The admin console (PRD-13) is a second Next.js deployment from the same repository on its own hostname (admin.deucex.ai) with its own staff authentication (magic link plus a mandatory passkey) and a separate database role whose grants are limited to what the console needs; decided 13 September (A18). It shares the component library and the API service, never the player session. This is a deliberately boring, well-documented stack chosen so a team of three to five can operate it without a dedicated platform engineer.

## 2. The data model

The schema below is derived directly from PRD-00 section 5.3 and the twelve agent data dictionaries. Types are indicative (Postgres types); every money-adjacent table is designed around M-DATA-1 (original currency, locked rate, never overwritten) and M-DATA-2 (receivables stay out of reserves until received).

### 2.1 The money model, worked through properly

M-DATA-1's own acceptance example is the test: an expense of €38.50 on 10 September must show, when the player switches home currency from AUD to USD, the USD amount at the 10 September rate, with the original €38.50 still visible underneath. The naive design (store the amount converted to whatever the home currency was at save time) fails this test the moment the player changes their home currency preference, because there is no way to re-derive a EUR-to-USD rate for 10 September from a stored EUR-to-AUD number without a second, un-auditable conversion.

The correct design keeps a small, append-only archive of daily ECB reference rates (ECB publishes each currency against EUR), and every money-bearing row stores only its original currency, its original amount, and the transaction date. Conversion to any display currency is then always a lookup against that date's archived rates, computed as original-to-EUR divided by target-to-EUR for that same date, never a live re-fetch and never an overwrite of a stored value.

### 2.3 The audit log (M-GATE-4)

Two tables, not one, because a scheduled run and a player approval are genuinely different events with different actors:

`agent_runs`: `id`, `agent_name`, `player_id`, `trigger_type` (`schedule`,`manual`,`event`,`threshold`), `started_at`, `completed_at`, `inputs_hash`, `model`, `prompt_version`, `schema_version`, `status` (`succeeded`,`failed_validation`,`failed_infra`,`degraded`), `output jsonb`, `cost_amount numeric`, `cost_currency`. A validation failure (the structured output does not parse against its Zod schema) is recorded as `failed_validation`, matching PRD-01's own language ("a validation failure is a failed run").

`approvals`: `id`, `player_id`, `agent_run_id` (nullable, since some approvals like a manual balance update have no agent run behind them), `action_type` (`entry_confirm`, `expense_save`, `balance_update`, `patron_send`, `content_publish`, `sponsor_send`, `retract`, `tier_change`, and so on), `payload jsonb`, `approved_by`, `approved_at`, `device`. Both tables are indexed on `(player_id, created_at)` and surfaced verbatim under Settings > Data & safety, per M-GATE-4 and ST-24.

A third table covers the staff side (PRD-13 AD-4, AD-5). `admin_actions`: `id`, `admin_id`, `role_at_time`, `player_id` (nullable for platform-wide actions such as a kill switch or a snapshot import), `action_type`, `target jsonb`, `consequence text` (the sentence shown at confirmation), `reason text` (a check constraint makes it non-null for `delete_account`, `comp`, `refund`, `snapshot_apply`, `provider_switch`), `device`, `created_at`, `notified_player boolean`. It is append-only (no update or delete grant for any role), indexed on `(player_id, created_at)` and `(admin_id, created_at)`, and its player-scoped rows are merged into the player's own Data & safety view marked as admin actions.

The console's database role can read `players` and the account-level tables and write only the tables in this section plus `admin_actions`, `share_links.revoked`, `players.tier_status`, `players.deletion_*` and agent schedule state. ## 3. Agent orchestration layer

A scheduled run starts as a row in a cron-populated queue table, not as a direct function call. A scheduler (Postgres `pg_cron` or an external cron hitting a small endpoint) enqueues one job per due agent per player, with an idempotency key of `(agent_name, player_id, scheduled_window)`. A unique constraint on that key means a retried or duplicated enqueue is a no-op rather than a second run, which matters because PRD-00's own non-functional requirement is that a failed scheduled run retries three times with backoff. The worker picks up the job, builds an input bundle (each field tagged with its source and an `as_of` timestamp), calls the structured-output LLM with a JSON schema, and validates the response with Zod before anything is written.

A validation failure is treated exactly as several PRDs specify: the run is marked `failed_validation` in `agent_runs`, the previous good output stays visible with a banner ("Sunday's run didn't complete, showing last week's list"), and the retry logic re-prompts once with the schema error included before falling back to the last-good state. This is deliberately narrow: retrying blindly against a model that keeps failing the same schema wastes money without helping the player, so after one corrective retry a failed run stays failed until the next scheduled trigger.

Degrading gracefully when one input feed is down is handled at the input-assembly step, not inside the prompt. Every input field carries `{value, as_of, stale}`; when the ATP feed, weather API or an ECB rate is unavailable, the bundle marks that field stale rather than omitting it silently, and the output schema always includes a place to say a value "was not refreshed," the same language PRD-01 and PRD-08 already specify in their failure-behaviour sections. This means a partial failure produces a labelled, partial answer rather than a hard failure of the whole run, matching the product's stated preference for showing uncertainty rather than hiding it.

The approval gate is the one part of this architecture that has to be enforced by code structure, not by convention, because convention is exactly what a future bug or a rushed feature will quietly break. The design is a single, small module (the actions module) that is the only code allowed to import the Stripe, Resend, or ICS-push clients, or write an `entry_decisions` row to `entered`, or transition a `prize_receivables` row to `received`. Every function in that module takes an `approval_id` as its first argument and, before doing anything, verifies against the `approvals` table that a matching, unconsumed, player-authored approval exists for that exact payload hash. Agents and LLM code never see these credentials and never call these functions directly; an agent's output is always a proposal row, and the only path from proposal to action runs through a player tap that creates the approval record first. This is enforced at review time by a lint rule (no other file may import the Stripe or Resend SDKs) and at runtime by the actions module refusing to run without a valid approval, so the gate cannot be bypassed by a rushed feature.

Pauses and kill switches (PRD-13 AD-15, AD-16) are checks at the job-pickup step, not inside agents: the worker reads `agent_schedules.paused` for the player and agent, and `provider_switches` for every provider the agent depends on, and if any is off it marks the job `skipped_paused` and moves on, so a switch takes effect on the next pickup with no code path that can bypass it. Held payouts under a payouts switch are queued rows in `payouts` with status `held` and released in `friday` order on resume.

Per-run cost accounting falls out of this design almost for free: every LLM call the worker makes is wrapped in a helper that records token counts and a cost estimate onto the `agent_runs` row it belongs to, using a small, manually maintained pricing table (model name to cost per token) that gets updated whenever a vendor changes pricing. This is also the mechanism behind the per-agent dashboards in section 5.

Elite's Agent Studio lets a player change an agent's cadence and adjust a constrained set of prompt parameters (tone, thresholds like the mood chart window, which categories always escalate for the Fan Agent). The schema validation, the approval gate and the five always-escalate categories in PRD-10 are platform code sitting outside the editable prompt template entirely; the player edits a small, typed configuration object (`agent_schedules.prompt_overrides jsonb`), not the system prompt or pipeline code. That is what makes "change schedules and prompts without breaking the gate" true structurally: there is no template slot into which an override could remove a schema check or a gate call, because those checks are not part of the template at all.

## 3a. Where MCP fits, and where it does not

The Model Context Protocol lets a model call tools and read resources through a standard server. Reviewed against this architecture on 14 September, it earns its place in two areas and would damage a third.

Not in the scheduled agents. Every agent run is a single schema-constrained call on a pre-assembled input bundle whose fields carry `{value, as_of, stale}`, hashed into `agent_runs` with a fixed cost. Letting the model fetch its own inputs through tools would make cost variable per run (the unit economics in section 5 are already over the cap), empty the inputs hash of meaning, move staleness labelling from the assembler into the model's judgement, and make a bad run harder to explain to a player. Feed ingestion, receipt and menu extraction and transcription are not agentic at all. No MCP in the Tournament, Financial, Content, Mindset, Conditions or Fuel agents in Release 1.

In building the platform. Several vendors in section 4 ship MCP servers, and the build plan hands Claude Code one step per session. Supabase's server applies migrations to a branch, reads logs and runs the security and performance advisors (most of build step 0.2 and every migration after it). Vercel's server reads deployments and build logs for both apps. Stripe's server configures test-mode products, prices and Connect settings for E7. Sentry and GitHub servers close the loop on errors and pull requests. None of this changes the product; it shortens the build. Rule: MCP writes go to database branches and vendor test modes only, never production.

In operating the platform. One server to write, in Phase 5 beside E18: a DeuceX admin MCP server over the console's API, exposing the read side (player lookup, agent health, feed status, cases, spend against cap) and the console's own actions (retry a run, extend a trial, resend a guardian email, set a deadline) under the same rules as the console: staff identity and role, a required reason for the AD-5 actions, an `admin_actions` row with actor `mcp:<admin>`, and every side effect through the actions module so nothing sends email or moves money without an approval row. For a team of three to five this turns "find why the morning batch failed for three players and retry them" into one request with the audit trail intact. About a week.

Plausible later. The Fan Agent (Release 2) is the one conversational agent and could ground itself through a read-only server over the answer bank, public results and published updates, but a fixed retrieval step does the same job at a fixed cost, so MCP only wins if the bank grows large. Agent Studio could expose a constrained tool set to Elite schedules. A player-facing server scoped to a player's own data, so a player can ask their own assistant "how long does my money last", is a Release 3 idea with a privacy review attached.

The honest risk statement: the ATP and ITF feeds are the two integrations that can sink the project, not because the engineering is hard but because the commercial and legal path to a licensed feed is opaque, slow, and priced through negotiation rather than a public rate card. The fallback that has to exist regardless is the manual-override ingestion path specified in PRD-13 (ranking snapshot CSV import with a per-player preview, fact-sheet corrections with a before-and-after diff, and deadline entry for events the ITF publishes late), so the product can soft-launch core value before a commercial feed is signed, as PRD-11's own "unverified" state already anticipates. Whether the CSV path is acceptable under the eventual ATP and ITF licence terms is an open question in PRD-13 section 12 and should be raised in the licensing conversation itself.

## 5. Unit economics of model spend

PRD-00 section 6 sets the ceiling: average Pro model and API spend under 15 percent of the Pro price, which is 15 percent of A$49, or A$7.35 a month. The table below builds the estimate the way the brief asks, agent by agent, from each contract's own stated cost target and a labelled assumption about how often that agent actually runs for an active Pro player in a month.

| Agent | Contract's own cost target | Assumed monthly volume (estimate, not from any PRD) | Estimated monthly cost |
|---|---|---|---|
| Tournament Agent | Under A$0.40 per run | Weekly schedule, about 4.3 runs a month | A$1.72 |
| Match Scribe | Under A$0.05 per note (transcription plus extraction combined) | 20 notes a month for an active Pro player (no monthly cap on Pro, unlike Free's 10) | A$1.00 |
| Financial Agent | Under A$0.10 per scheduled run, under A$0.02 per receipt | Daily schedule, 30 runs, plus 15 receipts a month | A$3.00 + A$0.30 = A$3.30 |
| Fans | Under A$0.03 per drafted note | 8 flagged patrons a month from the daily attention pass | A$0.24 |
| Content Agent | Under A$0.08 primary language (extra languages are Release 2) | 8 triggered drafts a month, one language (worksheet 9) | A$0.64 |
| Mindset Coach | Under A$0.08 per delivered insight | Daily, 30 a month | A$2.40 |
| Fuel | Under A$0.05 per scan | 15 scans a month | A$0.75 |
| Conditions and Equipment | Under A$0.03 per brief per run | 5 briefs per weekly Tournament Agent run (21.5 briefs a month) plus a small allowance for mid-week travel refreshes | A$0.65 + A$0.13 = A$0.78 |
| **Total** | | | **≈ A$10.83** |

Against the A$7.35 ceiling, this estimate sits at roughly 147 percent of target, about 22 percent of the Pro price rather than 15 percent. This is the honest answer to the brief's question: at these assumed usage levels, it does not currently hold, and the gap is real enough (about A$3.50 a month) that it needs a deliberate response rather than rounding error. The admin console's Money page shows the live figure daily against the cap and alerts the owner at 80 percent (PRD-13 AD-19), so the gap is watched from the first week rather than found at month end.

Two agents, Financial and Mindset Coach, account for over half the total (A$5.70 of A$10.83) precisely because they are the only two agents that run daily regardless of whether anything meaningful has changed. The single highest-leverage fix is to stop regenerating prose when the underlying numbers have not moved: the Financial Agent's "one thing to do this week" sentence and the Mindset Coach's insight both only need a fresh model call when their inputs materially change, not on a fixed clock. A cache keyed on the input hash, falling back to yesterday's text when nothing has changed, would plausibly cut both costs by 30 to 50 percent with no product-visible difference, since the player sees the same true statement either way.

The second fix is model tiering: a smaller, cheaper model for high-frequency, low-complexity generation (the Financial Agent's single sentence, the Conditions brief's comparison paragraph, Fuel's menu translation) and a larger, more capable model reserved for the infrequent, high-value prose that needs voice and judgement (Content Agent patron updates, Sponsor Agent outreach, Mindset Coach's insight, which has to get tone exactly right per M-PRIV-3). The prototype's earlier inconsistent references to three different models across agents (C3 in the review register, since replaced by generic "drafting", "extraction" and "structured-output" model labels, with the provider list disclosed only under Data & safety) suggest this tiering was already being felt intuitively during design; it should become a deliberate policy, and the model behind each label a configuration value, not copy.

Third, the Conditions brief is currently costed as one call per candidate, five calls per Tournament Agent run; batching all five into a single structured-output call, since they share the same forecast and fact-sheet inputs, should cut that line close to a fifth of its current cost. Fourth, per-tier rate limits (already specified for manual Tournament Agent re-runs, one an hour) should extend to any agent a player can trigger on demand, so a heavy user cannot single-handedly blow the average.

None of this is free effort: caching, tiering and batching are each a modest but real slice of work, probably two to three weeks combined, and should be scheduled as Release 1 work rather than assumed incidental. The other necessary step is measurement: the per-run cost field in `agent_runs` (section 3) should be watched from the first week of real usage, because the contracts' cost targets were set independently, agent by agent, without anyone checking whether they summed under the ceiling. They do not, and that should be treated as a finding from this exercise, not a forecast to be quietly revised down later.

## 6. Security and tenancy

Per-player isolation is enforced at the database layer with Postgres row-level security policies keyed on the authenticated player's id, so a bug in application code cannot leak one player's ledger or notes to another, materially stronger than isolation enforced only in middleware. Share-link tokens (coach and manager) are 128-bit random values, checked on every request against the `share_links` table rather than cached client-side; revocation (M-SHARE-3's one-minute requirement) is met by never caching token validity for more than a few seconds server-side, which at this traffic volume costs nothing meaningful.

Stripe holds all card data end to end, through Stripe Checkout for subscriptions and the Stripe customer portal for card changes; DeuceX's own PCI scope stays at SAQ A, the minimal self-assessment tier, because card data never transits DeuceX's servers. Encryption at rest is the default on both the managed Postgres provider and Cloudflare R2; encryption in transit is TLS everywhere. Secrets (LLM, Stripe, Resend and ranking-feed API keys) live in the hosting platform's own secret manager or a dedicated secrets tool, never in source control.

The audio and photo lifecycle from M-PRIV-1 (seven days, confirmed on 13 September, worksheet 3) is a scheduled worker, not a manual process: a daily job finds every `notes` row whose audio is older than seven days and unconfirmed, or whose transcript was confirmed since the last sweep, and deletes the R2 object, writing the deletion cause onto the row. Account deletion follows the same pattern: the player's confirmation link sets `deletion_effective_at` fourteen days out and puts the account in the pending state; a daily job executes deletions whose date has passed and writes a completion record, and a cancel (by the player, or by support at the player's request through the console) clears the date and restores the account (worksheet 4).

Staff authentication is separate from player authentication: magic link plus a mandatory passkey, no shared accounts, and a person who is both a player and staff holds two identities. Player sign-in is magic link with an optional passkey and no stored password (worksheet 11), which removes credential storage, password reset and breach-monitoring work from the platform entirely. Menu and receipt photos are deleted immediately after the extraction call returns, success or failure, with the same audit pattern; the ledger's receipt thumbnail is a separately generated rendition, never the original photo, so deleting the photo never breaks the ledger's display.

## 7. Privacy and compliance engineering

The Australian Privacy Act and the Australian Privacy Principles are the baseline, and most of what they require (an access and correction path, a clear collection notice, a nominated contact) is already covered by the export and settings surfaces PRD-12 specifies. GDPR, required for European players, adds two things needing real engineering rather than policy language: erasure and portability. Portability is the same export mechanism M-PRIV-2 already requires (JSON and CSV, including transcripts). Erasure is harder than "delete account," because it has to reach backups and any downstream processor (the LLM provider's logs, Resend's delivery logs, Stripe's records where Stripe's own retention rules allow it) within a reasonable time, not just the primary database; this should be an explicit, tracked deletion job with a completion record, not assumed from a deleted Postgres row.

Data residency is a genuine open question given the company is Australian and players are worldwide. Australia does not currently have a GDPR adequacy decision from the European Commission, so processing European players' data means standard contractual clauses need to sit behind every sub-processor (the LLM providers, Stripe, Resend, the hosting provider) rather than being assumed away. The practical recommendation for a team this size is one well-documented hosting region with strong SCC support from every chosen vendor, rather than multi-region residency, and to keep Settings > Data & safety explicit and current about which providers and regions are in use, as M-PRIV-4 already requires. This needs a few hours with a privacy-aware lawyer before Release 1 ships to any European player, not an engineering judgement call.

## 8. Observability

Every `agent_runs` row already carries what an observability layer needs: count, latency (`completed_at` minus `started_at`), and cost (section 3). Approval rate and dismiss rate need one more join: approval rate is the share of proposal-bearing runs with a matching `approvals` row within a reasonable window (say 48 hours), and dismiss rate is the share of patterns, drafts or brands explicitly dismissed rather than acted on. A nightly aggregation job into per-agent summary tables drives these dashboards without a dedicated analytics platform at Release 1 scale; Grafana against those tables, or even a simple internal page, is enough for a team of three to five.

The alert PRD-00 specifies, approval rate below 30 percent on any agent for two weeks, is a scheduled check against that summary table, firing to the owner by email or Slack; deliberately simple rather than a full alerting platform, since alert volume will be low and a missed one (an agent quietly failing to earn trust) is costly enough to want a human looking at every instance.

Against the 99.5 percent monthly availability target, the error budget is about 3.6 hours of downtime a month, tracked against a genuinely external uptime check rather than the hosting provider's own status page, with every deploy timestamped against the same log so a release-to-incident correlation is visible without archaeology.

## 10. Ranked technical risks and gating decisions

Ranked by how much damage each does if it goes wrong, from highest to lowest.

First, ATP, WTA and ITF ranking and calendar data. This is the single risk that can sink the project, and bringing the WTA into Release 1 (A21) adds a second licensing negotiation with a different body, because Tournament Agent, stage detection and the Conditions layer all sit downstream of it, and engineering effort alone cannot resolve it. Mitigation: start the licensing conversation in week one, before related code is written, and build the manual-override ingestion path as a first-class feature so the product can launch on hand-entered data if a commercial feed is not yet signed.

Second, the money model's correctness under M-DATA-1 and M-DATA-2. Mitigation: build the FX archive and the locked-rate ledger design (section 2.1) before any other agent that touches money, and write the currency-switch acceptance scenario from PRD-00 itself as an automated test before Release 1 ships, not after a bug report.

Third, the approval gate being enforced by convention rather than structure. Mitigation: the actions-module design in section 3, enforced by both a runtime check and a code-review lint rule, built as part of E12 before any agent is connected to real Stripe or Resend credentials.

Fourth, the unit economics genuinely exceeding the 15 percent ceiling at realistic usage, as shown in section 5. Mitigation: treat caching, model tiering and batching as scheduled Release 1 work, not a later optimisation pass, and instrument real per-run cost from the first week of usage rather than trusting the contracts' independently set targets to sum correctly.

Fifth, Stripe Connect Express's country coverage against a genuinely worldwide player base. Mitigation: check the actual country distribution of early players against Connect Express's supported country list before committing to a launch date, and have a fallback (a restricted launch market, or a manual payout process for unsupported countries) ready rather than discovered mid-onboarding.

The register decisions that gated these epics were all settled on 13 September 2026 (DECISIONS-WORKSHEET.md v0.2 and register A18 to A20), so no epic is now blocked on a product or legal call. The ones that shape the build most directly: the guardian flow and both verification paths are hard blockers inside E1; sign-in is magic link and passkey only, which simplifies E0; audio is deleted at seven days, which fixes E3's lifecycle worker; the patron fee is 8 percent on Pro and 5 percent on Elite applied to the gross with Stripe's charge stored separately, which fixes the `payouts` schema in E7 and the MRR figure in E4; the pending prize stays out of the P&L, already the E4 design; notifications are two categories per agent, which fixes E11 and E12's notification service; the delete-account cooling-off is fourteen days, built in E11 and the deletion job; patron updates are single-language in Release 1, which moves the multi-language work from E8 to E17; the Fan Agent label is permanent unless the player reviewed the reply, which is a schema check in E15; the admin console is a separate deployment, impersonation is out of Release 1, and model spend per player is visible to all console roles, which fix E18's shape. Two items remain product calls rather than blockers: whether the ranking CSV import is acceptable under the eventual ATP and ITF licence terms (raise it in the licensing conversation), and whether the distress-case on-call needs a rotation from day one (the owner holds it until there is a second person).
